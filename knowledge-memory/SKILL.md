# 知识库与记忆

配合 TokenHub MCP Server `knowledge-memory` 使用，提供知识库、长期记忆、Agent Skill 三组工具。
身份由 TokenHub Gateway 在 `/mcp/knowledge-memory` 注入；不要伪造 `x-tokenhub-user`，也不要操作
别人的记忆。

**知识库 = 组织的权威事实（同事也要能查到）；记忆 = 这位用户在项目里的历史、偏好与约束。**
两者冲突时以知识库为准，并把冲突告诉用户。

## 先判断要不要查

多数任务不需要检索。按下面的顺序判断：

- 当前工作区代码、本轮上下文、已注入的长期记忆能回答 → **直接干活，不检索**。
- 纯机械改动（重命名、格式化、修 typo、照已有模式加一个字段）→ **不检索**。
- 涉及项目约定、构建/测试/发布命令、架构与目录约定、命名规则、用户偏好、部署与权限边界
  → **查一次记忆**。
- 涉及公司/团队的规范、需求、指标、接口文档、业务流程、“我们是怎么做的” → **查一次知识库**。
- 用户说“继续刚才 / 按之前的约定 / 我偏好 / 我们项目里 / 查文档 / 看看资料” → 对应的那一种。

不要检索：通用编程知识、语言语法、公开 API、数学计算、当前工作区代码已经能回答的问题。

调用要少而准：一次 `memory_recall` + 一次 `kb_search` 通常就够。同一个问题最多两轮，第二轮必须换
更精准的关键词或范围。不要为了“更全”反复检索，也不要在回答里复述检索过程。

## 决策顺序

1. 组织事实优先 `kb_search`；用户偏好与项目约定优先 `memory_recall`。
2. 两者都可能相关时，先 `memory_recall` 取任务上下文，再 `kb_search` 查权威依据。
3. 知识库与记忆冲突时，以知识库为权威事实，并把冲突告诉用户。
4. 回答内部事实时注明来源文档名；来自记忆时说明这是历史约定或用户偏好。
5. 没有命中的记忆必须明说“没有找到”，不要虚构。

## 记忆：先用现成的，再检索

**上下文里可能已经有「长期记忆」段**（网关在会话开始时自动注入）。先看那段够不够，不够再用
`memory_recall` 补一次——注入的就是同一份记忆，不要重复检索。

但要注意**注入只在会话首轮做一次**，会话内不再更新。中途换过话题之后，那段注入的记忆已经和当前
问题无关了，这时候才是 `memory_recall` 真正该用的时候，不要因为「一开始注入过」就跳过它。

调用时传当前客户端的真实 `query`，**并始终传 `project` = 当前工作目录名**（如 `llm_token_hub`）。
省略 `project` 只会读到「通用记忆」，看不到你在项目里沉淀的结论。需要会话里的原始对话时设
`include_conversations=true`；需要核心准则时改用 `memory_core_read`。

`project` 由你声明：客户端不一定能识别出项目，识别不出时记忆会落进「通用记忆」。跨项目通用的个人
偏好（回复语言、语气）可以留在通用记忆里；项目约束、路径、部署方式必须带 `project`。

## 记忆：动手之前，先看有没有同类任务的经验

`memory_recall` 的命中里除了偏好与事实，还有**底座自动提炼的经验（`[经验]`）与轨迹（`[轨迹]`）**：
“上次做同类任务是怎么做的、踩了什么坑、为什么这么选”。准备做一件以前显然做过的事之前（部署、迁移、
排障、换配置、写同类脚本），先 `memory_recall` 搜一次，比重新摸索省事——这是 vibe coding 里最值钱
的一类记忆。

注意两点：

- **经验线分数偏低**，常排在事件/实体后面；一次没搜到就换个更贴近任务的说法再搜一次，别直接放弃。
- 经验与轨迹是**底座从会话归档自动产出的，只读**：不要往 `experiences/`、`trajectories/` 写，
  也不要改写它们。想让经验沉淀，正常干活即可；要写的是下面那些明确结论。

## 记忆：写什么、什么时候写

网关已经**自动**把每一轮对话追加进会话归档，**不要调用 `memory_capture`**（会记两遍）。你要判断的
是哪些结论值得立刻变成长期记忆，用 `memory_scene_write` 写死。

值得写（vibe coding 最常沉淀的几类）：

- 构建/测试/发布命令，以及“先跑 X 再跑 Y”这类执行顺序。
- 仓库约定：目录结构、命名规则、依赖与版本约束、生成代码放在哪。
- 架构与设计约束：“X 只能通过 Y 访问”“不要引入新依赖”“这个模块不碰网络”。
- 用户的协作偏好：回复语言、提交粒度、要先给方案还是直接动手。
- 明确边界：“不要动生产配置”“这个接口外部团队在用”。

不要写：

- 代码本身、文件内容、临时调试过程、一次性的报错。
- 工作区文档（README / AGENTS.md / 设计文档）里已有的东西——重复记录只会互相打架。
- 密码、Token、私钥、手机号、身份证等敏感数据。用户要求存凭据时，先建议改用平台的凭据存储，
  拒绝后也不要写入。

写入时机：任务告一段落、或用户确认结论时写一次，不要每改一个文件就写。宁可少写——一条稳定的
约定比十条临时观察有用。

**需要立刻生效就现在写，不要指望自动提炼**：底座要等会话攒够消息、token 到量或空闲一段时间才
批量提炼，刚说完的内容不一定马上能被搜到。

**路径与更新**：

路径必须相对且稳定（例如 `preferences/communication.md`），不要用临时会话路径。

- `preferences/<topic>.md`：沟通与协作偏好（长期保留）。
- `entities/<category>/<name>.md`：项目、服务、人物等实体（长期保留）。
- `events/<YYYY>/<MM>/<DD>/<topic>.md`：一次性事件（7 天后过期）。
- `cases/<topic>.md`：做法复盘（长期保留）。
- `experiences/`、`trajectories/`：**底座自动产出，只读**，不要自己写（见上一节）。
- **先召回再写**：写之前用 `memory_recall` 查一遍，同一主题已经有条目就改写那个 path，不要另起
  一条。两条讲同一件事的记忆会同时被召回，Agent 只能自己猜哪条还成立。
- **改写是覆盖，先 `memory_read` 读全文**：`memory_recall` 只给摘要，照摘要覆盖会把条目里没被
  摘到的那部分直接删掉。改哪个 path 就先读哪个 path；不确定这条记忆落在哪时用 `memory_grep`
  按字面搜（术语、路径、版本号、接口名这类），再用 `memory_ls` 看清那一层有什么。
- **一个实体只留一张卡**：`entities/` 下不要按主题或阶段加后缀新开并列卡——「X 部署」「X 部署配置」
  「X 采集」是同一个实体，应当合并进 `entities/<category>/x.md` 一张。category 也要和已有卡片保持
  一致：同一个实体换个 category 就是换了个路径，两张卡永远不会合到一起。
- **控制长度**：一条事实不超过 300 字符，实体卡不超过 1200 字符。长期记忆共用同一个注入预算（网关
  注入块总共 4000 字符），写长了会被截断，还会把别的记忆挤出去。
- **结论被推翻时改写原路径，不要并列新增**：同一个结论只维护一条路径。用户说“以前那条不适用了 /
  现在不用兼容了 / 已经反过来”，就 `memory_scene_write` 到同一个 path 覆盖旧内容，并在正文带上
  时间（如“2026-09-13 起不再需要兼容 X”）。两条互相矛盾的长期记忆会同时被召回，Agent 只能自己猜。
- **临时性约束写带日期的 `events/`**：“这个接口暂时不能动 / 下周再删这个字段 / 先用某个绕法”这类
  会过期的约束，写进 `events/<YYYY>/<MM>/<DD>/<topic>.md` 让它按 7 天自然过期；写进
  `preferences/`、`entities/` 等于钉成永久规则，过期后仍会被召回并干扰判断。
- **带日期才会过期**：保留期只清理 `events/<YYYY>/<MM>/<DD>/` 这种布局。扁平的
  `events/<事实名>.md`（记忆底座自动提炼产出的就是这种）不会过期，靠改写覆盖。想让一条约束自己
  消失，就必须写成带日期目录的路径。

**保留期**：会话归档只留最近 7 天（每天北京时间 04:10 清理），事件类记忆同样 7 天过期；偏好、实体与
核心准则长期保留。

## 知识库

`kb_search` 默认返回上下文，适合 Agent 自己组织答案。返回前会把分块里的 `<drawing>`/`<table>` 标记
还原成 Markdown——插图变成带短期直链的图片、表格变成 GFM 表格，原样引用即可，不要转述标记本身。
客户端不渲染远程图片时（Codex 桌面端），把插图改写成 `[图注](直链)` 链接，或按下面 `kb_images`
那节的办法先落盘再引用。

| 参数 | 默认 | 何时调整 |
|---|---:|---|
| `mode` | `mix` | 一般内部问题保持 `mix`；精确术语用 `hybrid`，局部机制用 `local`，主题综述用 `global`，只要纯切片召回用 `naive` |
| `only_need_context` | `true` | Agent 保持 `true`；只有希望引擎直接生成最终答案时才传 `false` |
| `top_k` | `8` | 问题宽泛、来源分散时提到 12~20；精确查询保持 5~8 |
| `enable_rerank` | `true` | 保持开启；确认要更快、更原始的召回时才关闭 |
| `include_chunk_content` | `true` | 需要核对原文或引用时开启；只看文档名和结论时可关闭 |

`kb_id` 缺省为公司库；涉及特定项目时先用 `kb_list` 拿到该项目 `kb_id` 再传。

**要图时用 `kb_images`**：文档里的插图、流程图、组织架构图、界面截图在切片里存的是 `<drawing>` 标记而不是
图片本体，`kb_search` 只会把标记还原成图片链接，不返回图片本体。当结论依赖图上内容（如流程节点、图中标注、
截图里的报错），或用户明确要求看图时，调用 `kb_images`：它按同样的方式召回切片，再把被引用的插图作为
MCP 图片块返回，并附文字上下文与来源。工具刻意不做结构化输出，图片块不会被 `structuredContent`
顶掉，模型自己一定收得到图；用户能不能在对话里**看到**图则取决于客户端渲染，按下面对号入座。
默认最多 3 张、单张上限 2MB，可用 `MCP_KB_IMAGE_MAX_BYTES` / `MCP_KB_IMAGE_MAX_COUNT` 调整。

摘要里每张图都给一条 **Markdown 链接**（默认 1 小时有效），图注优先取 VLM 生成的图片名，
取不到时是“文档名 + 第 N 张插图”；没命中插图时摘要会说明原因（超限、取图失败、文档没图），
照实转述，不要含糊成“没有这张图”。链接过期重新调用 `kb_images` 换新即可。
注意摘要给的是 `[图注](直链)` **链接**语法；要内联显示图片时，把同一条直链改写成
`![图注](直链)` 图片语法即可，直链本身不要截断或改写（签名在 query 上）。

**图怎么给用户**：先分清两个位置——MCP 图片块只出现在**工具卡片**里，正文是另一回事。
用户说的“图文混排”基本都指**正文里有图**，所以正文该配图就写图片语法，不要只丢一句
“见图 1”，也不要只给一条“备用链接”。

**该取图就直接取，不要反问**：模型最常见的毛病是回一句“需要我把流程图调出来给你看吗”。
报销流程、操作步骤、表单、界面截图、设备说明这类问题有图才讲得清，直接在这一轮调用
`kb_images` 把图放进正文再回答——反问只会白耗一轮。只有用户明显只要一句结论
（如“报销上限是多少”）时，才不必取图。

`kb_search` 只还原出链接、不给图片本体，所以“链接够不够”很容易被判成够；判断标准是
**问题要不要看清图上的内容**，而不是手上有没有链接。

1. 工具卡片里已经显示了图 → 讲结论即可；正文仍需配图时照样写 `![图注](直链)`，位置跟着结论走
   （控制台 `/chat` 的 system prompt 就是这么要求的）。
2. 工具卡片不显示图、但客户端渲染远程图片（Cherry Studio、OpenClaw Control UI 等）→ 用标准
   Markdown **图片**语法 `![图注](直链)`，直链整条原样塞进括号里；只写 `[图注](直链)` 或裸 URL
   就只是可点击文字，不会显示图。
3. Codex 桌面端等**按客户端安全策略不加载远程图片**的场景 → 图片语法只会渲染成点不动的占位符，
   必须给**链接**：`[图注](直链)`；要让用户直接看到图，先落盘再用绝对路径引用：

   ```bash
   mkdir -p /tmp/kb-images
   curl -fsSL -o /tmp/kb-images/1.jpg "<直链>"   # 文件名用 ASCII，避免 Markdown 转义问题
   ```

   然后写 `![图注](/tmp/kb-images/1.jpg)`——这条路在 Codex 桌面端实测可渲染。落盘目录用 `/tmp`
   或工作区临时目录，别提交进仓库，也别一直留着。

**什么该进知识库（而不是记忆）**：别人也需要查到的东西——团队规范、需求与决策、接口与流程文档、
可复用的模板和结论。只对你自己有意义的内容留在记忆里，否则同事搜不到。

导入：

- 用户明确说“导入 / 存进知识库 / 加入公司文档”。
- 用户要求把某个文件或当前已确认的结果沉淀为组织知识。

不导入：中间过程、未确认方案、临时日志、含密钥的内容。

优先导入原始文件（`kb_import` 的 `paths`）；没有对应文件时才用 `content` 传已确认的文本结论，并用
`title` 起一个可检索的来源名。导入是写操作，目标库需要有导入权限；不确定目标时先 `kb_list` 并请
用户确认，不要静默写入。文档被新版本取代时先问用户，不要重复导入造成两份并存。

## 核心准则与协作画像

涉及长期准则、跨项目偏好或团队规范时，先 `memory_core_read` 了解当前内容。它一次返回两份，性质
不同：**核心准则**（soul.md）是用户确认过的长期规则，优先遵守；**协作画像**（identity.md）是角色、
技术栈、常驻项目、协作方式这类背景，只当参考，不是用户提出的要求。

仅在用户明确确认规则/偏好/准则时调用 `memory_core_write` 写核心准则；写入是全量覆盖，先读再写，
不要凭猜测覆盖。**协作画像不要手工写**——它由记忆底座按对话自动收敛，手工覆盖等于把它变成第二份
准则。

## 安全与边界

- 记忆与知识库是组织内部资料：不要写进公开仓库、提交信息、外部服务或给外部人看的内容里。
- 不要把记忆整段复述给用户（他刚说过，或系统已经注入）；只在结论影响决策时引用一句。
- 删除记忆、文档或 Skill 前必须先跟用户确认，这是不可恢复的数据面操作。

## 何时沉淀 Skill

完成一段可复用流程，或用户明确说“沉淀为 Skill / 保存工作流”时，调用 `skill_extract`。提交的
`messages` 必须包含至少两条有效消息，优先保留用户目标、关键决策、工具调用、成功结果和注意事项。

需要复用已有流程时先 `skill_search`，找到后用 `skill_get` 读取全文，再执行。开始复杂工作前可调用
`skill_listing` 了解当前有哪些可用 Skill。

用户明确要求沉淀新 Skill 时调用 `skill_create`（content 用 Claude Skills 的 SKILL.md 格式，
frontmatter 必须含 name/description）；更新已有 Skill 先 `skill_get` 确认内容，再 `skill_update`
整体替换。

## 工具速查

| 工具 | 何时用 |
|---|---|
| `kb_list` | 首次使用知识库、确定 `kb_id`，或导入前确认范围 |
| `kb_search` | 检索组织权威事实；内部事实、业务规则、项目文档优先用它 |
| `kb_import` | 导入本机文件或已确认结论；先 `kb_list` 确认目标库 |
| `kb_documents` | 列出文档状态、分块数和时间；整理或删除前定位目标 |
| `kb_images` | 取回文档插图本体；结论依赖图上内容、或用户明确要看图时用 |
| `kb_status` | 查看文档状态统计和解析管线进度 |
| `memory_recall` | 检索当前项目的长期记忆，可选同时检索会话归档 |
| `memory_ls` | 列出记忆树一层，读/写某条之前先看清这一仓里有什么 |
| `memory_read` | 读某条记忆全文（`memory_recall` 只给摘要）；改写前必须先读 |
| `memory_grep` | 按字面/正则找术语、路径、版本号、接口名；语义近似用 `memory_recall` |
| `memory_capture` | 手动补写会话归档；网关已自动写入，正常不要调用 |
| `memory_scene_write` | 把已确认的规则、约束或工作流写入稳定路径（结论被推翻时改写同一路径，不要并列新增） |
| `memory_core_read` | 读取核心准则与协作画像（画像只读，由底座自动收敛） |
| `memory_core_write` | 全量覆盖核心准则（先读再写；画像不在这里写） |
| `skill_listing` / `skill_search` / `skill_get` | 发现和读取可复用 Skill |
| `skill_create` / `skill_update` / `skill_extract` | 新建、更新、从对话抽取 Skill |

## 隔离与可删除性

- 记忆按 TokenHub **用户 + 项目**隔离：同一用户在同一项目下的任意 Agent（Codex、Claude、OpenCode）
  共享同一份记忆；不同项目互相不可见，也无法跨用户读写。项目由调用方的 `project` 参数声明，
  省略即「通用记忆」。
- 用户可在 Console「知识库与记忆」查看、搜索、删除知识库文档、记忆与 Skill；核心准则在
  「核心 → 工作准则」查看和编辑（同页的「核心画像」只读）。
